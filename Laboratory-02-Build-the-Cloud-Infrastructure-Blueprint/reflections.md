Reflection

This activity made cloud computing feel far less abstract to me. Before this, terms like "compute" and "storage" were just textbook vocabulary. But once I was running commands on my own KillerCoda machine and seeing real results — my own CPU specs, my own RAM, my own IP address — the concepts finally clicked in a way that reading alone never achieved.

1. Which component is most important? I'd choose compute resources. Chapter 2 explains that compute provides the processing power needed to run applications and execute operations, and that matches my own take: storage is inert without something to use the data, and a network has nothing worth reaching if nothing is actually running. That said, digging deeper made me realize these four components are deeply interdependent — compute still needs somewhere to store its output and a way to be accessed.

2. How does Linux support cloud computing? This makes much more sense now. The module notes that Linux remains the leading operating system for cloud servers, and my own experience backs that up — every task in this lab was done through a Linux terminal, with no graphical interface involved.

3. Why does documentation matter before deployment? This was the most surprising part. I didn't think a "write it down" step could matter so much until the module's example of a university LMS struggling during enrollment due to limited hardware. That made it clear: you can't diagnose or scale a system you never properly documented.

4. New skills learned: Reading system specs from the command line, comparing AWS, Azure, and GCP services directly, and building my first real architecture diagram in Draw.io.

5. Portfolio improvement: My GitHub now shows actual progression rather than a single isolated activity — two labs in, it's starting to read like a developing skill set.
